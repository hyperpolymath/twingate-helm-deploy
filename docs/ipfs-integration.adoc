= IPFS Integration Guide

This guide explains how to expose IPFS services via Twingate for secure external access.

== Architecture Overview

----
┌──────────────────────────────────────────────────┐
│  External Users                                   │
│    └── Twingate Client                           │
│              ↓ Authenticated Access               │
├──────────────────────────────────────────────────┤
│  Twingate Connector                              │
│    └── Routes: ipfs-gateway, ipfs-api            │
│              ↓ Access Control                     │
├──────────────────────────────────────────────────┤
│  IPFS Private Swarm (on ZeroTier)                │
│    ├── Gateway: Port 8080 (HTTP)                 │
│    ├── API: Port 5001 (HTTP RPC)                 │
│    └── Swarm: Port 4001 (P2P, mesh-only)         │
└──────────────────────────────────────────────────┘
----

== Why Twingate for IPFS?

**Traditional IPFS Access Problems:**
1. **Public gateways** expose content to anyone
2. **No authentication** for private swarms
3. **Port exposure** creates attack surface
4. **No audit trail** of who accessed what

**Twingate Solves:**
1. **Identity-based access** - Only authenticated users can access gateway
2. **Fine-grained permissions** - Separate access for gateway vs API
3. **Zero exposed ports** - No NodePort/LoadBalancer needed
4. **Complete audit log** - Track all IPFS access by user

== Deployment Order

[source,bash]
----
# 1. Deploy ZeroTier (foundation)
cd zerotier-k8s-link

# 2. Deploy IPFS overlay (uses ZeroTier mesh)
cd ../ipfs-overlay

# 3. Deploy Twingate (access layer)
cd ../twingate-helm-deploy

# 4. Configure Twingate Resources for IPFS
# (via Twingate Admin Console)
----

== Twingate Resource Configuration

Create two Resources in Twingate Admin Console:

**Resource 1: IPFS Gateway (Read-only)**

[source,yaml]
----
Name: "IPFS Private Gateway"
Address: ipfs-gateway.ipfs-system.svc.cluster.local
Port: 8080
Protocol: HTTP
Access Groups:
  - All Engineers (read-only)
  - Data Scientists (read-only)
Security:
  - Require MFA: Yes
  - Session timeout: 8 hours
----

**Resource 2: IPFS API (Admin only)**

[source,yaml]
----
Name: "IPFS Admin API"
Address: ipfs-api.ipfs-system.svc.cluster.local
Port: 5001
Protocol: HTTP
Access Groups:
  - IPFS Admins (full access)
Security:
  - Require MFA: Yes
  - Session timeout: 1 hour
  - Audit all operations: Yes
----

**Key Point:** Gateway is read-only (CID retrieval), API has write access (pin, add, rm). Separate permissions.

== Service Labeling

Label IPFS services for Twingate discovery:

[source,bash]
----
# Gateway service
kubectl label svc ipfs-gateway -n ipfs-system \
  accessible-via-twingate=true \
  twingate-access-level=read

# API service (admin only)
kubectl label svc ipfs-api -n ipfs-system \
  accessible-via-twingate=true \
  twingate-access-level=admin
----

## User Workflow

**Accessing IPFS Gateway:**

[source,bash]
----
# 1. Start Twingate Client
twingate start

# 2. Authenticate (OIDC/SSO)
twingate login

# 3. Access gateway via internal DNS
curl http://ipfs-private-gateway:8080/ipfs/Qm...
# OR
curl http://ipfs-private-gateway:8080/ipns/example.com

# Gateway resolves to actual service via Twingate
----

**Accessing IPFS API (Admins only):**

[source,bash]
----
# Add content (requires admin access)
curl -X POST -F file=@document.pdf \
  http://ipfs-admin-api:5001/api/v0/add

# Pin CID (requires admin access)
curl -X POST \
  "http://ipfs-admin-api:5001/api/v0/pin/add?arg=Qm..."
----

Users get **authenticated, audited access** to IPFS without VPN or exposed ports.

== Network Policy Coordination

*Twingate NetworkPolicy:*
[source,yaml]
----
egress:
  - to:
      - namespaceSelector:
          matchLabels:
            name: ipfs-system
      - podSelector:
          matchLabels:
            app: ipfs
    ports:
      - protocol: TCP
        port: 8080  # Gateway
      - protocol: TCP
        port: 5001  # API
----

*IPFS NetworkPolicy:*
[source,yaml]
----
ingress:
  - from:
      - namespaceSelector:
          matchLabels:
            name: twingate-system
    ports:
      - protocol: TCP
        port: 8080  # Gateway
      - protocol: TCP
        port: 5001  # API
----

**Key Point:** IPFS swarm port (4001) is NOT exposed via Twingate. Only gateway/API.

== Security Considerations

**Principle: Twingate exposes gateway/API, NOT swarm**

[source,bash]
----
# ✓ ALLOW: Twingate → Port 8080 (Gateway, read-only)
# ✓ ALLOW: Twingate → Port 5001 (API, admin-only)
# ✗ DENY: Twingate → Port 4001 (Swarm, internal mesh only)
# ✗ DENY: Direct external access to IPFS
----

**Access Control Matrix:**

| User Group | Gateway (8080) | API (5001) | Swarm (4001) |
|------------|----------------|------------|--------------|
| All Engineers | ✓ Read | ✗ | ✗ |
| Data Scientists | ✓ Read | ✗ | ✗ |
| IPFS Admins | ✓ Read | ✓ Write | ✗ |
| Internal Mesh | ✗ | ✗ | ✓ (ZeroTier only) |

**Audit Trail:**

Twingate logs all access:
- Who accessed which CID
- When and from where
- Success/failure status
- Bandwidth used

Example audit query:
[source,bash]
----
# Twingate Admin Console → Audit Logs
# Filter: Resource="IPFS Private Gateway"
# Shows: user@example.com accessed /ipfs/Qm... from 203.0.113.5 at 2026-01-22 16:00 UTC
----

## Monitoring Integration

**Prometheus Metrics:**

Twingate-IPFS metrics:
- `twingate_ipfs_requests_total{resource="ipfs-gateway"}` - Total requests
- `twingate_ipfs_bandwidth_bytes{direction="egress"}` - Data transferred
- `twingate_ipfs_auth_failures_total` - Authentication failures

IPFS metrics (via gateway):
- `ipfs_http_requests_total{handler="gateway"}` - Gateway requests
- `ipfs_blocks_sent_total` - Blocks served
- `ipfs_gateway_latency_seconds` - Response time

**Grafana Dashboard:**

Correlate Twingate access with IPFS performance:
- High Twingate requests + high IPFS latency = Scale gateway
- High auth failures = Investigate access policies
- Unusual CID access patterns = Potential abuse

## Troubleshooting

**Users can't access gateway:**
1. Check Twingate Client status: `twingate status`
2. Verify user is in correct access group (Twingate Admin Console)
3. Check Twingate Connector health: `just status`
4. Verify IPFS gateway pod is running: `kubectl -n ipfs-system get pods`

**Gateway works but content not found:**
1. Check CID is pinned: `ipfs pin ls | grep <CID>`
2. Verify IPFS swarm is connected: `kubectl -n ipfs-system exec -it ipfs-0 -- ipfs swarm peers`
3. Check ZeroTier mesh: `just mesh-status` (in zerotier-k8s-link)

**API access denied (admins only):**
1. Verify user is in "IPFS Admins" group
2. Check MFA is completed
3. Review Twingate audit logs for rejection reason
4. Confirm API service is running: `kubectl -n ipfs-system get svc ipfs-api`

## Example: Complete Stack with Proven ZKP

Combine Twingate authentication with `proven` library for content verification:

[source,bash]
----
# 1. User accesses gateway via Twingate (authenticated)
curl http://ipfs-private-gateway:8080/ipfs/Qm... > document.pdf

# 2. Verify integrity with ZKP (no re-download needed!)
curl http://verisimdb-api/verify \
  -d '{"cid": "Qm...", "proof_type": "content_integrity"}'

# Response:
# {
#   "valid": true,
#   "verified_by": "proven_library",
#   "confidence": "cryptographic",
#   "bandwidth_saved": "1.2 GB"  # Didn't need to re-download!
# }
----

**Benefits:**
- Twingate authenticates WHO can access
- Proven verifies WHAT they're accessing (without re-fetching)
- Audit trail tracks WHEN they accessed
- ZeroTier encrypts HOW it's transmitted

## Performance Characteristics

*Twingate overhead for IPFS:*
- **Latency:** +10-20ms vs direct access
- **Throughput:** ~950 Mbps (no significant degradation)
- **Authentication:** <100ms (cached after first auth)

*Full stack (Twingate + ZeroTier + IPFS):*
- **Gateway response:** <50ms for cached CIDs
- **Large file transfer:** ~900 Mbps sustained
- **Multi-user concurrency:** Scales with Connector replicas
